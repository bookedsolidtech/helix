# AAA Story Template

This page is the canonical reference for documenting a component that has earned **WCAG 2.2 Level AAA + peer-standards certification**. New cert'd component story files should follow this pattern so the public-facing docs page reads as **conformance documentation**, not as a CEM control enumeration. Existing certified component MDX may not yet conform to every detail of this template — it's a forward-looking standard that supersedes the prior per-component layouts.

The pattern surfaces evidence in priority order: real-world usage first, conformance evidence second, ARIA/keyboard contract third, consumer obligations fourth, the full audit fifth, and CEM-driven variant gallery last.

---

## Section order (top → bottom)

1. **Hero usage scenario** — hand-authored Lit template inside a component story (e.g., a sign-in form, a patient-lookup widget). The first thing a reader sees must be the component working in real context.
2. **A11yStatusCard** — auto-rendered by `HelixDocsPage` (the Storybook autodocs template). Pulls `helixMeta.aaa.*` from CEM. No author action required.
3. **AAA Conformance Card** — the `AAAConformanceCard` component. Renders one row per WCAG 2.2 AAA + peer criterion with verdict, plain-language summary, spec link, and N/A justification. (Per-criterion numeric thresholds are documented in `scripts/aaa-standards.json` for now and surface on the conformance row only when authored into the audit's `Measured:` field — the card does not yet read thresholds from a structured source.)
4. **ARIA Pattern Card** — the `APGPatternCard` component. Cites the W3C APG pattern, renders the keyboard contract as `<kbd>` clusters, and documents the expected screen-reader announcement.
5. **Consumer obligations** — the `ConsumerObligations` component. Hand-curated from the AAA-AUDIT.md "Known consumer obligations" section.
6. **Live state demos** — hand-authored stories for focus, hover, disabled, error, and loading states with annotated descriptions.
7. **Inline AAA-AUDIT.md** — the `InlineAuditPanel` component. A collapsible details element with the full audit text inline. Vite `?raw` import gives the docs bundle the source-of-truth markdown without a build step.
8. **Variant gallery** — at the bottom, smaller. CEM-driven control iteration belongs here, not at the top of the page.

## Reference template

This is the canonical MDX scaffold. Copy it verbatim, then customize the hero scenario, screen-reader announcement, and consumer obligations for the target component.

```mdx
{/* hx-button.mdx — AAA-cert'd story page for hx-button (replace tag for your component) */}

import {
  AAAConformanceCard,
  APGPatternCard,
  ConsumerObligations,
  InlineAuditPanel,

// AAA-AUDIT.md it pulls from lives four levels up under packages/hx-library.
import auditRaw from '../../../../packages/hx-library/src/components/hx-button/AAA-AUDIT.md?raw';

<Meta title="Components/Button/Conformance" />

<div className="hx-docs">

## hx-button — sign-in form context

[Hero usage scenario goes here — show the component WORKING, not enumerated.]

## How to read the badges

The green "AAA Certified" badge above is rendered by the autodocs template
from `helixMeta.aaa.*` in `custom-elements.json`. Each criterion chip is
expanded into the row-level evidence below.

<AAAConformanceCard tag="hx-button" />

<APGPatternCard tag="hx-button" screenReaderAnnouncement="Submit, button" />

<ConsumerObligations
  tag="hx-button"
  obligations={[
```

## Why this order

<SectionHead title="Documentation, not enumeration" meta="--editorial-priority" />

A docs page that opens with `<hx-button variant="primary">…</hx-button>` followed by 24 variant tiles is a CEM regurgitation. A docs page that opens with a real sign-in form, then proves the component clears AAA on every applicable Success Criterion, then walks through the keyboard contract, then warns the consumer about author-CSS footguns, is **conformance documentation**.

Healthcare deploys make procurement decisions on conformance documentation. The variant gallery is reference material; the conformance evidence is the differentiator.

<SectionHead title="Live data, never hand-typed" meta="--source-of-truth" />

The `AAAConformanceCard` pulls verdicts from `@helixui/library/aaa-verdicts.json` — a slim snapshot of the formal harness output (`.reports/formal-aaa-audit/audit.json`) regenerated automatically by every `pnpm aaa:audit` run via `scripts/generate-aaa-verdicts.mjs`. The `APGPatternCard` reads `@helixui/library/custom-elements.json`. The `InlineAuditPanel` pulls live from the source `AAA-AUDIT.md` via Vite `?raw`.

The verdict snapshot is committed to the repo so the docs build is deterministic; drift between the docs surface and the cert payload is bounded by the cadence at which the audit is re-run. When a re-audit lowers a verdict, the slim snapshot regenerates and the docs card re-renders the new verdict (Supports / Partially Supports / Does Not Support / Not Applicable) on the next build. Per-component `AAA-AUDIT.md` regeneration is a **separate** step today (`node scripts/regenerate-audits.mjs`) — it is not yet chained into the default `pnpm aaa:audit` pipeline. Re-run both to keep the cert payload + per-component audit file aligned.

<SectionHead title="Consumer obligations are editorial" meta="--curated" />

The only hand-curated section is `<ConsumerObligations>`. Obligations reflect editorial judgment about which footguns to flag for the target audience and live in story source so they evolve with the component contract. The obligations list should **align with** the "Known consumer obligations" section in the component's `AAA-AUDIT.md` — strict mirroring is the goal, but scenario-specific editorial additions are permitted when a particular usage pattern surfaces an obligation that does not generalise to the audit text. Reviewers should keep the two sources directionally consistent.
