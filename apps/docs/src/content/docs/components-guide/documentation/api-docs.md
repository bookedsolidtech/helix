HELiX API documentation is generated automatically from two sources: JSDoc comments in component source files and the Custom Elements Manifest. This page explains the full pipeline from source to published docs.

## The Generation Pipeline

```
Component source (.ts)
  → @custom-elements-manifest/analyzer
    → custom-elements.json
      → HELiX docs site (Astro Starlight)
        → Published API reference pages
```

Each component's JSDoc annotations produce entries in `custom-elements.json`. The docs site reads the manifest at build time and renders property tables, event tables, slot documentation, CSS part references, and CSS custom property overrides.

## `@helixui/library` Public API Surface

The public API of `@helixui/library` consists of:

- **Custom element tag names** — `hx-button`, `hx-dialog`, etc. (registered in the browser)
- **Component class exports** — `HelixButton`, `HelixDialog`, etc. (for TypeScript types)
- **CSS custom properties** — `--hx-button-bg`, `--hx-card-shadow`, etc. (theming API)
- **CSS parts** — `::part(button)`, `::part(label)`, etc. (structural styling)
- **Slots** — named and default slots
- **Events** — custom events with typed detail payloads

Everything documented with JSDoc tags and exported from the package is considered public API and subject to semver versioning.

## Viewing API Docs Locally

The HELiX docs site is an Astro Starlight app in `apps/docs`:

```bash
pnpm run dev --filter @helixui/docs
```

Component API reference pages are auto-generated from `custom-elements.json` during the build. Run the CEM generation step first if you have changed component source:

```bash
pnpm run cem --filter @helixui/library
pnpm run dev --filter @helixui/docs
```

## Versioning API Docs

API docs are versioned alongside the package. Each major version has a dedicated docs URL:

```
https://helix.bookedsolid.tech/v1/
https://helix.bookedsolid.tech/v2/
```

Breaking changes between major versions are documented in a migration guide linked from the changelog.

## Breaking Change Documentation

A breaking change is any modification to the public API that requires consumers to update their code. For HELiX components, this includes:

| Change type | Example |
|---|---|
| Removed property | Deleting `hx-button.inverted` |
| Renamed property | `size` → `hx-size` |
| Changed property type | `variant: string` → `variant: 'primary' \| 'secondary'` |
| Removed event | Removing `hx-focus` event |
| Changed event detail shape | Removing `detail.originalEvent` |
| Renamed CSS part | `container` → `base` |
| Renamed CSS custom property | `--hx-btn-bg` → `--hx-button-bg` |
| Changed slot name | `icon` → `prefix` |

When introducing a breaking change:

1. Bump the major version in `package.json`
2. Add a `@changesets/cli` changeset: `pnpm changeset add`
3. Document the breaking change in `CHANGELOG.md` with a migration example
4. Update or add a migration guide in the docs site

## CHANGELOG Format

HELiX follows the [Keep a Changelog](https://keepachangelog.com) format:

```markdown
## [1.2.0] - 2026-03-26

### Added
- `hx-button`: `full` property for full-width layout
- `hx-button`: `inverted` property for dark-background contexts

### Changed
- `hx-badge`: `size` prop now accepts `'xs'` (previously minimum was `'sm'`)

### Fixed
- `hx-dialog`: Focus trap no longer captures Tab events outside the dialog

### Breaking Changes
- `hx-button`: Renamed CSS part `container` to `base`. Update `::part(container)` to `::part(base)`.
```

Changesets are generated by `@changesets/cli` and automatically assembled into `CHANGELOG.md` during the release process.

## HELiX Docs Site Generation Pipeline

The docs site build executes these steps in order:

1. `pnpm run build --filter @helixui/tokens` — compile token CSS
2. `pnpm run build --filter @helixui/library` — compile components + generate CEM
3. `pnpm run build --filter @helixui/docs` — Astro static site build reads CEM + markdown

The Astro build reads `custom-elements.json` and generates API reference pages for each component declaration. MDX component pages import and render the `<ApiTable>` component which consumes the CEM data.

## Keeping Documentation Accurate

The CEM is the authoritative source. If the manifest is out of date, the docs site will show stale information. Run `pnpm run cem` before committing any component API changes.

CI enforces this with a step that regenerates the manifest and checks for a diff:

```yaml
- name: Check CEM is up to date
  run: |
    pnpm run cem --filter @helixui/library
    git diff --exit-code packages/hx-library/custom-elements.json
```

If `custom-elements.json` is not committed or is out of sync with source, CI fails.
