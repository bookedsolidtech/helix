# Custom Workflows

The HELiX protoMaker system routes features through **custom workflows** — YAML-defined pipelines that control which phases run, which agent role handles the work, and how git operations are managed. Choosing the right workflow ensures your feature lands in the right hands without unnecessary overhead.

There are 8 workflows available. Each is described below with its purpose, active phases, agent routing, and guidance on when to use it.

---

## How Workflows Are Selected

Workflows are matched to features using two mechanisms:

- **Categories** — explicit category tags on a feature (e.g. `audit`, `docs`, `fix`)
- **Keywords** — terms in the feature title or description that trigger automatic routing

You can assign a workflow explicitly when creating a feature, or let the platform route based on category and keyword matching.

## helix-audit

**Description:** Read-only component quality audit — intelligence gathering only, no code changes.

### Phases

| Phase   | Enabled |
| ------- | ------- |
| INTAKE  | Yes     |
| PLAN    | No      |
| EXECUTE | Yes     |
| REVIEW  | No      |
| MERGE   | No      |
| DEPLOY  | No      |

### Agent Routing

- **Role:** `principal-engineer`
- **Model:** `sonnet`
- **Tools:** Read, Grep, Glob, Bash

### Git Behavior

No worktree, no commits, no PR. Output is written to `.automaker/audits/`. The feature terminates at `done` status automatically.

### When to Use

Use `helix-audit` when you need a quality sweep of a component or set of components without making any changes. The agent reads source, runs analysis, and produces a written report. Use this before planning remediation work, as an input to batch audit cycles, or to validate quality after a release.

**Match categories:** `audit`, `quality-audit`
**Match keywords:** audit, sweep, analyze, quality

No worktree, no commits, no PR. Output is written to `.automaker/audits/`. The feature terminates at `done` status automatically.

Use it before any accessibility remediation sprint or when a component's a11y compliance is in question.

**Match categories:** `a11y-audit`, `accessibility-audit`

## helix-docs

**Description:** Documentation updates — streamlined pipeline, no architectural planning.

### Phases

| Phase   | Enabled |
| ------- | ------- |
| INTAKE  | Yes     |
| PLAN    | No      |
| EXECUTE | Yes     |
| REVIEW  | Yes     |
| MERGE   | Yes     |
| DEPLOY  | No      |

### Agent Routing

- **Role:** `technical-writer`
- **Model:** `sonnet`

### Git Behavior

Uses a worktree. Auto-commits, auto-pushes, and auto-creates a PR targeting `dev`. Auto-merges the PR on approval. The feature terminates at `review` status.

### When to Use

Use `helix-docs` for any documentation-only change — new guide pages, updating existing MDX content, fixing typos, adding examples, or restructuring the docs site navigation. The PLAN phase is skipped because documentation changes rarely require architectural decisions. The full PR pipeline runs so the docs build is validated in CI before merge.

**Match categories:** `docs`, `documentation`
**Match keywords:** docs, documentation, guide, readme

Use `helix-component` for all new component work — initial implementation, major feature additions, or complete rewrites. The DEPLOY phase handles npm publishing if configured.

**Match categories:** `component`, `component-impl`

## Examples

### Creating a feature with explicit workflow assignment

When using the protoMaker board, set the workflow field when creating or updating a feature:

```
workflow: helix-fix
category: fix
title: Fix keyboard trap in hx-modal focus management
```

### Triggering audit workflows via keywords

Feature titles containing recognized keywords automatically route to the matching workflow:

```
# Routes to helix-a11y-audit
title: Accessibility audit for hx-select component

# Routes to helix-perf-audit
title: Bundle analysis for hx-data-table

# Routes to helix-audit
title: Quality sweep of hx-form components
```

### Chaining audit and fix workflows

A common pattern is to run an audit first, then create fix features from its findings:

1. Create a feature with `helix-audit` — the agent writes findings to `.automaker/audits/`
2. Review the audit report
3. Create targeted fix features with `helix-fix` — one per issue or logical group
4. Each fix feature goes through the full PR pipeline independently

This pattern keeps audit (read-only, no PR) and remediation (code changes, PR) cleanly separated, and gives you control over which findings to act on.

### Batch audit workflow

For auditing many components at once, use the batch audit strategy:

1. Create a single `audit/deep-quality-batch-YYYYMMDD` branch
2. Run audit agents sequentially on the shared branch
3. Consolidate findings into a single report
4. Create `helix-fix` features for each remediation task

See the batch audit scripts in `scripts/` and orchestrator in `.automaker/agents/audit-batch-orchestrator.js`.
